# Relay

The Digestif relay: a Cloudflare Worker with D1 and a Durable Object per circle, in TypeScript. It
implements [spec/digestif-relay.json](../spec/digestif-relay.json) and the relay rules in
[docs/protocol.md](../docs/protocol.md), and passes the relay cases of the suite in
[conformance/](../conformance). One deployment hosts many circles, each at its own address,
`<base>/c/<the 64 hex digits of its root>` (docs/protocol.md, Hosted circles). Its home circle,
`HOME_ROOT`, is its operator's own, and a circle route without an address answers `410 circle_moved`
naming the home circle's; a freshly deployed relay has none and hosts nothing. Every other circle opens with its root's bootstrap append, vouched
for by a member of a circle the relay already hosts.

The relay's own routes, outside every circle:

| Route | What it does |
|---|---|
| `GET /v0/version` | Unsigned: `relay_version` alone, the same value `GET /v0/circle` reports (`{}` when unstamped), so anyone can read which release a relay runs. |
| `GET /v0/relay` | Unsigned: `relay_version`, `mailer` and the mailer's `encryption_key`, `hosting` (whether it opens a new circle now), `home` (the home circle's root, `null` with none) and `last_unprefixed_at`, the last request on a circle route without a circle's address. |
| `GET /v0/invites/:invite_key` | The bootstrap read across every hosted circle: the dinner listing an open invite, to the invite key alone, with `circle`, the address of the circle it opens. |

Each circle's routes, under its address and nowhere else:

| Route | What it does |
|---|---|
| `POST /v0/envelopes` | Append one signed envelope: the request check, the envelope check, the chain rules, the daily cap, then the admission fold. |
| `GET /v0/envelopes?after&limit` | Everything after a cursor in `relay_id` order; circle state in full, content from the reader's join epoch on. |
| `GET /v0/circle` | The root, the epoch, the `admission_cutover`, the admitted keys, the limits and `relay_version`, the relay release the Worker was built as (absent when unstamped). |
| `GET /v0/invites/:invite_key` | The bootstrap read of this circle's invites. |
| `POST /v0/mail` | Mailing relay only: opens the sealed mail request and the digest it names, emails the digest with one answer link per option through Resend, and remembers the digest hash (`already_sent` on a repeat). |
| `GET /v0/links/:id?s=` | The confirm page for an answer link: the item and the option, one Confirm button. Changes nothing. |
| `POST /v0/links/:id` | Confirms the link: checks the pre-signed decision, appends it, marks the item's links used. |
| `/app/` | The phone app: static assets from `app/`, `index.html` for any path the build has no file for. |

The three mailer routes answer `404 not_mailer` on a relay whose `MAILER` is not `"1"`. A circle the
relay does not host answers `404 circle_unknown`, a circle route without an address `410 circle_moved`
(its message and `Location` header naming the home circle's address), a suspended one `410
circle_suspended` at every route, and the home circle answers a write `503 moving` (`Retry-After: 5`) for the seconds its move
into its store drains ("Each circle's store").

## Configuration

Worker variables, in `wrangler.jsonc` (`vars`) or per deployment with `wrangler deploy --var`:

| Variable | Meaning | Default |
|---|---|---|
| `HOME_ROOT` | `sha256:<hex>` of the home circle's root (a circle, or a founding dinner): the operator's own circle, which carries the relay's releases, needs no voucher and is the address an unprefixed circle route names. Left unset by the setup below; `digestif circle found --relay` sets it, and every deploy keeps it. | unset: no home |
| `CIRCLE_ROOT` | The home circle while `HOME_ROOT` is unset, as a deployment configured before relays hosted many circles names it. | the conformance test circle's root, at the top level only |
| `HOSTING` | `"off"` (or `"0"`) stops the relay opening new circles: a founding answers `403 not_hosting`. | on |
| `RELAY_STORAGE` | Bytes every hosted circle's reserved `CIRCLE_STORAGE` must fit in together: a founding past it answers `507 relay_full`. Under the Workers Free plan's 5 GB of Durable Object storage. | 4294967296 (4 GiB) |
| `CIRCLE_STORAGE` | Bytes one circle's store may hold, and the share each reserves: an append past it answers `507 circle_full`. At most 1 GiB on the Free plan. | 268435456 (256 MiB) |
| `CIRCLES_PER_MEMBER` | Circles one vouching member may open per 30 days: past it a founding answers `429 too_many_circles`, naming the day the next opens. | 5 |
| `MOVE_ROWS_PER_DAY` | Rows a day the home circle's move copies from D1 into its store; `0` keeps it on D1 (the top level, for the tests and `wrangler dev`). | 20000 |
| `MAX_ENVELOPE_BYTES` | Envelope plus body. | 65536 |
| `MAX_APPENDS_PER_DEVICE_PER_DAY` | Per author, UTC day. | 500 |
| `MAX_PAGE_SIZE` | `GET /v0/envelopes` page size. | 500 |
| `SKEW_SECONDS` | Request clock skew either way; also how long nonces are kept. | 3600 |
| `MAILER` | `"1"` on the one relay that mails (docs/protocol.md "Mailer routes"); anything else and the mailer routes answer `not_mailer`. | `"0"` |
| `RELEASE_SIGNERS` | A `digestif-signers-v0` document the admission fold starts from in place of the build's `node/update/release-signers.json`. Set only at the top level, to the conformance suite's public test signers; no deployed environment sets it. | the build's `release-signers.json` |
| `MAIL_FROM` | The From header of the digest email, an address on the circle's domain. | `Digestif <digest@mail.digestif.io>` |
| `RELAY_URL` | The URL answer links name, when the relay is reached through another address than the request's origin (a tunnel in front of `wrangler dev`). | the request origin |
| `SITE_HOST` | The circle's bare domain, on which the relay answers `/install.sh` and nothing else: the install template rendered from the newest published node manifest that every key of the build's `release-signers.json` signed, never `RELEASE_SIGNERS` (`src/install.ts`, docs/releases.md "The hosted install script"). Unset, the relay serves no `/install.sh`. | unset |

Secrets, set with `wrangler secret put`, required when `MAILER` is `"1"` and unread otherwise:

| Secret | Meaning |
|---|---|
| `RELAY_SEALING_KEY` | The mailing relay's X25519 private key, raw 32 bytes, base64url. Its public half is the `mailer` key in the `relay` body the operator's node posts; digests and mail requests are sealed to it. |
| `RESEND_API_KEY` | Resend's API key; the Worker sends through `https://api.resend.com/emails` and nothing else. |

The D1 binding is `DB`, database `digestif-relay`, which holds what spans circles (the hosted
circles and the invite index, `migrations/0006_hosted_circles.sql`) and the home circle's tables
until it has moved; `CIRCLE_STORE` binds each circle's store; the assets binding is `ASSETS`,
directory `app/`. Apart from the mailer's two secrets the relay holds no key of its own; every
request is proved by the signatures it carries, an answer link by the secret in its URL, and a new
circle by its founder's voucher. A store is named by its circle's root, so two circles are never
mixed.

**The relay version is not a variable.** `GET /v0/circle` and the unsigned `GET /v0/version` report
`relay_version`, the relay release the Worker was built as, from `RELAY_VERSION_STAMP`, a constant the build defines while it bundles
the Worker (`wrangler deploy --dry-run --outdir <dir> --define 'RELAY_VERSION_STAMP:"0.3.0"'`), so it
is part of the signed bytes and no deployment setting can change it. A Worker bundled without the
define reports no `relay_version` field at all.

The checked-in top-level `CIRCLE_ROOT` is the conformance suite's throwaway test circle, so a fresh
clone runs the suite with no setup; it is for local runs only. A deployment sets no root: it starts
with no home, and its operator's `digestif circle found --relay` writes `HOME_ROOT`. Every file
sets `keep_vars`, so a `wrangler deploy` keeps the `HOME_ROOT` the deployment holds.

## Building and testing

Node.js 23.6 or later (the conformance suite runs `.ts` files directly) and npm.

    npm ci
    npm run check        # wrangler types, tsc, eslint
    npm test             # vitest inside workerd, against a fresh local D1
    npm run conformance  # the suite's relay cases against two wrangler dev instances

`npm run check` first generates `worker-configuration.d.ts` with `wrangler types` (the runtime
types for the compatibility date and flags; not checked in, so an editor wants `npm run types` once). `npm test` runs five files: the routes
before any envelope, the whole conformance relay suite in-process through the Worker with the
fold invariant below checked after every accepted append, the races (`test/race.test.ts`): two
appends interleaved at every point of the check through an injected D1, since miniflare
serializes D1 access over HTTP and cannot stage a real one, the mailer routes and `/app/` against a
fake Resend endpoint (the test's own `fetch`; nothing leaves the isolate, and the Worker under
test is configured as the mailer with a sealing key from `node/mail/test/vectors.json`), and the
email rendering against the snapshots in `test/fixtures/` (`npx vitest run -u` rewrites them after
a deliberate change). `npm run conformance` starts `wrangler dev`
on a temporary local D1 per instance, each on a port the OS reports free (`--port N` uses N, N+1
instead), applies the migrations, runs
`conformance/bin/digestif-conformance.ts relay --url …` and exits with its status; `--instances 1`
runs one relay (the two-relay cases are skipped), `--case relay.clock` narrows the run, and
`--bundle DIR` runs every instance on an unpacked relay release bundle as it stands: its module
not bundled again, its `app/` and its migrations, which is how the relay release build tests the
bytes it packs (`ci/relay-bundle.sh`, docs/releases.md, Relay releases).

`ci/build.slow.sh` runs all three when `relay/` is present. `app/` is generated and never tracked:
`scripts/app.sh` fills it with `ui/build` when the UI was built and with `placeholder/index.html`
otherwise, and `npm run dev`, `test`, `conformance` and `types` run it first, so a build leaves
`git status` clean. The tests only need the placeholder: they check the route, not the UI.

Locally, for a relay that keeps its state between runs:

    npm run migrate:local
    npm run dev          # http://127.0.0.1:8787

## Deploying

The same Worker is deployed once per relay, each a wrangler environment in `wrangler.jsonc`: today
`dinners` and `dinners-roman` (docs/design.md "Two relays to start"). wrangler does not inherit variables,
assets or bindings into an environment, so each repeats them; the top-level configuration is for
`wrangler dev` and the tests only.

| | `dinners` | `dinners-roman` |
|---|---|---|
| Cloudflare account | the project's ("Digestif", held by Mike Bryzek) | Roman Cherkasov's own |
| Worker, database | `digestif-dinners`, D1 `digestif-dinners` | `dinners`, D1 `digestif-dinners-roman` |
| Address | custom domains `dinners.digestif.io`, and `digestif.io` for `/install.sh` | its `workers.dev` address, `dinners.<Roman's subdomain>.workers.dev` |
| `MAILER` | `"1"`, the one relay that mails | `"0"`, never mails |
| `RELAY_URL` | `https://dinners.digestif.io` | a placeholder, replace it with the relay's URL |
| `SITE_HOST` | `digestif.io` | unset |
| Secrets (`secrets.required`) | `RELAY_SEALING_KEY`, `RESEND_API_KEY` | `RELAY_SEALING_KEY` |

Both name the founding circle as their home with `vars.CIRCLE_ROOT` (dinner 2's dinner message),
which the Worker reads while `HOME_ROOT` is unset. A new relay's environment names no root: it
starts with no home. Placeholders to fill before the first deploy: `RELAY_URL` of `dinners-roman`,
and the `database_id`s, which the deploy script fills.

Deploy with `npm run deploy -- <environment> [--dry-run] [--release <version>]`
(`scripts/deploy.sh`; `--release` is "Operations", Break glass); an environment `wrangler.jsonc` does
not define is refused, naming the ones it does. Without `--release` it prints the account, the
environment and its home circle (none on a new relay; `ROOT_HASH` sets `HOME_ROOT` at deploy time),
creates the D1 database when its
id is still the placeholder (and writes the id into `wrangler.jsonc`; commit that), refuses unless
the web UI is built (`ui/build`, which `scripts/app.sh --require-ui` copies into `app/`), applies the
migrations with `wrangler d1 migrations apply DB --remote --env …`, reads the database's circle row
when there is a home (see "Re-root"), and runs `wrangler deploy --env …`, which keeps the variables
the deployment holds. `--dry-run` prints that plan
and touches nothing. Run `wrangler login` as
the account's holder first (or set `CLOUDFLARE_API_TOKEN` in the shell, never in a file).

The account needs a `workers.dev` subdomain, a relay on a custom domain included: without one
Cloudflare refuses the upload of a release that carries a Durable Object migration (403, code
10063). Opening Workers and Pages once in the account's Cloudflare dashboard creates it.

1. Generate the relay's X25519 key: `node scripts/keygen.mjs` prints `RELAY_SEALING_KEY=…` (the
   secret, base64url raw private key) and `public=x25519:…` (the `encryption_key` of the `relay`
   message). Set the secret with `npx wrangler secret put RELAY_SEALING_KEY --env <environment>`,
   pasting the value at the prompt. A relay that does not mail never reads it.
2. On `dinners` also set `RESEND_API_KEY` (see "Operations").
3. `npm run deploy -- <environment>`. The relay starts with no home circle: `GET /v0/relay` answers
   `home: null`, and it hosts nothing, since no circle on it can vouch for one.
4. The operator founds their first circle on it with `digestif circle found --relay <url>`, which
   writes the new root into `HOME_ROOT`, appends it and posts the circle's `relay` message: `url`,
   `mailer` and, for a mailer, `encryption_key`, which `GET /v0/relay` reports. Every later circle
   is founded by a member of a circle the relay hosts, vouched by their node for it.

To run the suite against a deployment rooted in the test circle:

    node conformance/bin/digestif-conformance.ts relay --url https://relay.example

A relay that already holds earlier runs is as good a target as a fresh one (conformance/README.md).

## Re-root

Only a home circle still held in D1 has a root to mismatch: every other circle's store is named by
its root, so a store never mixes two circles. The home circle's first request of any kind, even an
unsigned `GET /v0/circle` that answers 401, writes the database's `circle` row from the home root,
and the Worker refuses a database whose row
names another root: every route answers `500 misconfigured`. An isolate checks the row once and
then trusts it for reads; every append reads it again, so a row re-rooted under a running isolate
refuses that isolate's writes. So a relay first deployed on the
conformance test circle and then redeployed with a real `ROOT_HASH` on the same database serves
nothing until that row goes.

`scripts/deploy.sh` reads the row and the log size after the migrations:

| The database | What the script does |
|---|---|
| has no row, or names the configured root | deploys |
| names another root and holds no envelope | says so and asks; on `y` it deploys and then clears the row, `DELETE FROM circle` guarded on the old root and an empty log; without a terminal or a `y` it stops before deploying |
| names another root and holds envelopes | refuses: that is another circle's log, and the two are never mixed |

The row is cleared after the deploy, not before, because a request still reaching the old Worker
writes its root back; the script reads the row again and says to run it again if that happened.

A circle whose database holds another circle's log moves to a new database, under the same name:
export the old one if its log matters ("Export a database"), delete it with
`npx wrangler d1 delete digestif-dinners` (or `-2`), set the environment's `database_id` in
`wrangler.jsonc` back to `00000000-0000-0000-0000-000000000000`, and deploy, which creates the new
one and writes its id (commit that). The address stays; nodes push their logs to it on their next
sync.

## Operations

Every command runs in `relay/`, with `--env dinners` or `--env dinners-roman`, as the holder of that
environment's Cloudflare account (dinners: the project's account; dinners-roman: Roman's). The relay has
no health route and grows none outside the spec; to see that one is up and which release it runs,
read `GET /v0/version`, which needs no key (`curl https://dinners.digestif.io/v0/version`).

**Deploy.** A relay release reaches a relay through its operator's node (docs/releases.md, Relay
releases); nothing here is needed for it. `npm run deploy -- dinners` (see "Deploying") deploys a
build of the checkout, which is how a new relay gets its first deploy. Migrations are applied before
the Worker is replaced and only ever add.

**Break glass: deploy a signed release by hand.** When the operator's node cannot deploy (the first
relay release, which a relay running a checkout build cannot accept as an announcement; an operator
away for good, when GOVERNANCE.md's backup holder deploys with that account's break-glass access; a
node whose deploy keeps failing), deploy the release both signers signed, never a build:

    npm run deploy -- dinners --release 0.1.0

It runs nothing against the account until every check has passed:

1. downloads `manifest.json` and the combined `manifest.sig.json` from the version's GitHub release,
   `https://github.com/digestif-ai/digestif/releases/download/relay-v<version>/`
   (`DIGESTIF_RELEASES` names another place holding `relay-v<version>/`, a url or a directory), and
   refuses a version with no published release;
2. checks the signatures with `digestif-update verify --expect-version <version>`, which prints
   `signed NAME` or `missing NAME` per signer and passes only when every key of the release signer
   set signed and none is revoked. The `digestif-update` is never the release's own: `DIGESTIF_UPDATE`
   names one, else the node's (`<data dir>/good/bin/digestif-update`), else one on `PATH`, else the
   `digestif-update-<platform>` of the newest version the release list on main names that no recall
   takes out (the channel branch's list while main's names none);
3. downloads the bundle the manifest names and checks its sha256 and size against the manifest
   before unpacking it, then that its `migrations/` are exactly the manifest's, each with its
   sha256 (`scripts/release.ts`);
4. deploys those bytes as "Deploying" does, with the bundle in place of the checkout: its
   migrations applied with `wrangler d1 migrations apply`, the circle-row check of "Re-root", and
   `wrangler deploy` of the bundle's module as it stands (not bundled again) with its `app/`, under
   this environment's own name, routes, vars and database from `wrangler.jsonc`, tagged
   `relay-v<version>` and annotated with the bundle's sha256, the tag and annotation the operator's
   node gives its own deploys.

`--dry-run` does steps 1 to 3 and prints the plan, touching no account. A release that fails a
check is refused with what failed, and nothing is deployed. Log in as the account's holder first, as
for any deploy. Afterwards `GET /v0/version` (unsigned) and `GET /v0/circle` report the release's
`relay_version`, and the operator's node sees it on its next sync.

**Roll back.** To a signed release: `npm run deploy -- dinners --release <the earlier version>`
(Break glass). To the Worker version that served before: list versions with `npx wrangler deployments list --env dinners` (or
`npx wrangler versions list --env dinners`), then `npx wrangler rollback <version-id> --env dinners`
(without an id, the previous version). A rollback changes the code, not the database: after a
release with a new migration, roll back only to a version that works on the migrated schema.

**Watch it.** `npx wrangler tail --env dinners` streams logs and exceptions live; add
`--status error` for failures only. The relay logs no request body, secret or address.

**Export a database.** `npx wrangler d1 export digestif-dinners --remote --output dinners.sql`
(add `--no-schema` for data only). The file holds the whole log, sealed digests included, so keep it
as private as the relay. A `.sql` export restores into a fresh database with `wrangler d1 execute`.

**Rotate the Resend key** (dinners). In Resend, create a new API key, then
`npx wrangler secret put RESEND_API_KEY --env dinners`, paste it, and delete the old key in Resend.
A secret change takes effect at once with no redeploy. Nothing has to be told to the circle.

**Rotate the sealing key** (dinners; dinners-roman holds one it never reads). Run `node scripts/keygen.mjs`
and `npx wrangler secret put RELAY_SEALING_KEY --env dinners` with the new private value. Digests and
mail requests are sealed to the mailer's public key, so the circle must see a new `relay` message
for dinners naming the new `x25519:` public key before nodes seal to it: post it first, and put the
secret in the moment the circle has it. Anything sealed to the old key before nodes learn the new one
cannot be opened by the relay; those digests must be written again.

**When a relay is lost.** Nothing is lost: every node holds a full copy of the log and writes to
every relay it knows, so the circle keeps working on the others. To replace it, deploy again with the
same root hash (new D1 database, migrations, secrets, `npm run deploy`), keep the same address, and
nodes push their logs back on their next sync. A lost mailer additionally needs its sealing key
(set a new one and announce it as above) and `RESEND_API_KEY`; email stops until then.

**Resend secret** (dinners, in the project's Cloudflare account). The Worker is `digestif-dinners`; the secret is `RESEND_API_KEY`:

1. In Resend, make an API key with send access for the `mail.digestif.io` domain.
2. `cd relay && npx wrangler login`, signed in to the "Digestif" account.
3. `npx wrangler secret put RESEND_API_KEY --env dinners`, and paste the key at the prompt (or use
   Workers & Pages, `digestif-dinners`, Settings, Variables and Secrets, add a Secret with that name).

## Each circle's store

`CircleStore` (`src/store.ts`) is the store each circle a relay hosts keeps its state in: one
SQLite-backed Durable Object per circle, named by its root, holding its log, its fold output, its
invites, nonces and daily counts and, on a mailing relay, its mailed digests and links. The relay's
D1 keeps the registry of hosted circles (root, when it opened, which circle and member vouched,
`open` or `suspended`, which store answers it, size and last append) and the invite index.

- **The home circle moves on first use.** A relay deployed before it hosted many circles holds its
  home circle in D1. Its first request makes its registry row and, unless `MOVE_ROWS_PER_DAY` is 0,
  starts the move (`src/move.ts`): the store's alarm copies the next 500 rows by `relay_id` and
  records the last copied id in the same transaction, at most `MOVE_ROWS_PER_DAY` rows a day, while
  D1 serves the circle (`moving`). Once the copy catches up the row goes `draining`: D1's triggers
  refuse every append, mailed link and mailed digest that would land in its tables and the relay
  answers them `503 moving`, reads still answer from D1, and the alarm copies the tail and the
  circle's other tables, then sets `object`. Every route answers from the store after that, with
  every `relay_id`, `received_at` and `judged_at` kept.
- **Founding limits.** A founding that passes the voucher check opens the circle only while
  `HOSTING` is on, its member has opened fewer than `CIRCLES_PER_MEMBER` circles here in 30 days,
  and every hosted circle's `CIRCLE_STORAGE` share, the new one's included, fits in
  `RELAY_STORAGE`; a store refuses an append once it holds its share.
- **Suspending a circle** is the operator's, after the fact: `state = 'suspended'` on its registry
  row (`digestif relay suspend`, through Cloudflare's D1 query API with the deploy token) answers
  `410 circle_suspended` at every route of it until it is `open` again. Nothing reads its contents.

- **The adapter.** `circleDatabase(env.CIRCLE_STORE, root)` answers a `D1Database` handle over the
  circle's object, so the relay's query sites run against it unchanged. The handle keeps the
  object's id and takes a stub on every call, since a stub cannot outlive the request that made it.
  Each statement, or each batch, is one call: a batch runs inside one transaction, all or none.
- **Refusals.** An expected refusal (a lost race, a replayed nonce, `link_used`) crosses the call as
  a value and the adapter rethrows its text, which the relay matches as it matches D1's.
- **The schema.** The object applies every migration it lacks on first use, recorded in
  `d1_migrations` as `wrangler d1 migrations apply` records them. The Worker is one bundled module,
  so the migrations travel in `src/schema.ts`, which `node scripts/schema.ts` writes from
  `migrations/`; `test/store.test.ts` fails when it is stale.
- **The binding and the migration tag.** `wrangler.jsonc` binds `CIRCLE_STORE` at its top level and
  in each environment, and lists the migration steps at its top level only. A tag is never edited
  once released; a new class is a new step with a new tag. `bundle.json` carries both, and the
  operator's node uploads the Worker script rather than a version for a release whose tag the
  relay has not applied (docs/releases.md, The deploy step).

`npx vitest run --config vitest.do.config.ts` runs the whole suite with the Worker's `DB` swapped for
a store (`spike/`, DIG-319), but for the move, which needs D1 apart from the store.

## The phone app

`/app/` serves the node's web UI built for a phone (docs/protocol.md "The phone"): `ui/build`,
copied into `app/` by `scripts/app.sh` (and `scripts/deploy.sh` refuses to deploy without it), behind the assets binding with `run_worker_first`, so the
Worker strips the prefix and answers `index.html` for any path the build has no file for. On the
relay the phone app calls `GET /v0/envelopes` (signed by its own device key, from before it is
admitted until it finds its `device` envelope and from then on to read the member's items, digests
and decisions, the `item_answer`s on each question, and the member's newest `deny_list`, which its
deny layer checks every answer against), `POST /v0/envelopes` for its decisions and its
`item_answer`s (sealed to a question's readers, or the signed plaintext answer to a circle
question, which it writes only once it has read a `deny_list`), and `GET /v0/circle`. Pairing
(`POST /v0/_pair` in `ui/mock/relay.ts`) is the node's route, not the relay's: the pairing code is
pasted into the local UI and the laptop appends the `device` envelope that enrolls the phone.

## Design

**The fold is shared, not copied.** `src/` imports `conformance/src/fold.ts`, `envelope.ts`,
`keys.ts`, `encoding.ts` and `request.ts` by relative path and wrangler bundles them, so the relay
and the suite can never disagree about who is admitted. Those modules use `node:crypto` (Ed25519
through `createPublicKey` and `verify`, `createHash` for sha256) and `Buffer`. The Worker runs them
unchanged under the `nodejs_compat` compatibility flag: workerd's `node:crypto` verifies Ed25519 and
hashes sha256, which `test/worker.test.ts` proves on the test circle's root dinner inside workerd,
and `wrangler dev` showed the same before the flag was chosen. No bundler alias and no WebCrypto
twin, because the fold is synchronous and WebCrypto is not; a twin would have meant a second
Ed25519 implementation.

**D1 holds the log and the fold's output.** `envelopes` is the append-only log in relay order;
`admitted_keys`, `invites` and the `circle` row (root and epoch) are derived from it; `nonces` and
`daily_appends` serve the request checks. The shared `Fold` keeps its state in memory and exposes no
way to load it, so the relay replays it from the circle-state envelopes (dinner, join, device,
revoke, card, relay, release_revocation, release_recall, relay_release, signer_set, prompt) with
each one's `relay_id` as position and its `judged_at`, else its `received_at`, as clock, applies the
new envelope, and writes the envelope and the keys that changed to D1 in one batch. The invariant,
checked by `test/conformance.test.ts` after every accepted append: `admitted_keys`, the epoch and
the open invites equal a full refold of the log.

An isolate keeps the fold it last built (`foldCache` in `src/db.ts`): an append reads the ids of the
circle-state envelopes below its position, and when they begin with exactly the ones the kept fold
read (position, hash and clock), it folds a copy of that fold forward over only the envelopes
committed since; otherwise, a database swapped under the isolate or a cold isolate, it replays the
whole set. A committed circle-state append keeps its own fold, so the next append in the isolate
replays nothing. A replay marks each envelope `stored`, which skips the admission check and the key
signatures inside a join, device or revoke: the fold verified them when it accepted the envelope.
A retract, which folds its target too, replays without the kept fold.

**The relay_id is chosen first** (`MAX(relay_id) + 1`), before the duplicate, the fold, the chain
and the retract target are read, and every one of those reads sees only the log below it. So the
fold's positions and the rows agree, and the UNIQUE on `relay_id` guards the whole check: whatever
another append commits after the position was chosen takes that id, the batch fails, and the loser
re-runs the storage step once over the longer log (two joins at once take consecutive epochs; a
fork that races the envelope it forks is refused). The request is authenticated once, before the
retry, so its nonce is spent once and the re-run is not refused as a replay. A nonce is recorded
with a single INSERT against the `(key, nonce)` primary key; two copies of one request arriving
together cannot both pass.

**Retracts of circle state are refused** (`422 malformed`): a retract drops its target's body, and
the fold reads the bodies of dinners, joins, devices and revokes, so dropping one would leave the
log unfoldable for the relay and every node. The protocol fixes retracts for content; this is the
relay's reading until it says otherwise.

**The mailer stores nothing it was told.** `POST /v0/mail` opens the request and the digest with
the sealing key, renders the email with every option's link URL in it, and before calling Resend
takes a two-minute lease on the digest in `mail_claims` (a request that finds a live lease mails
nothing and answers `503 mail_failed`, which the node retries on a later pass) and writes each link's
id, the item it answers (column `ask`) and expiry in `links`, so the link routes can find the sealed
answer in the digest body the log already holds. The digest hash goes in `mailed_digests` (the
`already_sent` record) only once Resend has accepted the mail. A Worker that dies between the two
leaves a lease that expires, so the next request mails the digest rather than answering
`already_sent` for mail that never went; every send carries the Resend idempotency key
`digestif-mail/<digest hash>`, so a retry after a send that did go is answered by Resend and not
mailed twice. A send Resend refuses drops the request's own lease and the link index so a retry
mails (`502 mail_failed`). No column anywhere holds the request, a secret, the
address, the subject or a line of the plaintext; `test/mailer.test.ts` dumps every table after a
send and looks for each. The link pages all answer `200 text/html` as the spec lists, and `GET`
checks the link in this order: unknown, the secret, used, expired, so a page says no more about a
link than its secret earns. `POST` runs `checkAnswer` from `node/mail/webcrypto/mail.mjs` against
the admitted, unrevoked mail keys of the digest author's identity and then the core append path
(`appendSigned`, with no request signer, as a bootstrap append), so the chain rules, the daily cap
and the fold apply to the decision as to any envelope; a refusal is rendered, not returned as JSON.
The conformance suite has no `relay.mail.*` or `relay.links.*` cases: a black-box case would have a
real relay send email and would need the relay's sealing key, so the mailer's cases are vitest
cases here instead.

**Pages and email.** The answer-link pages and the digest email take their look from the web UI:
`src/theme.ts` holds the font stack, the stone text and background colors in light and dark, the plum
accent, the radii, the 4px spacing scale and the status tones, each commented with the token in
`ui/src/app.css` or `ui/src/lib/components/` it was copied from. The pages inline that stylesheet
(no external resource, no script); the email expresses the same values as inline styles, since mail
clients ignore stylesheets. The values are copies, so they can drift. The ask to Mike: export the
`ui/` theme as a shared CSS file (the `@theme` tokens and the status tones as plain custom
properties) so the UI, the pages and the email read one source.

**Where the protocol is silent, the relay follows the suite's choices** (conformance/README.md):
`not_admitted` is 401 for a request and 422 for an envelope, `too_large` is 422, and a second join on a
spent invite is `not_admitted`.
